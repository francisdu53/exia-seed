## 1 — Méthode

La revue ne s'est pas contentée de relire le code. Elle a suivi quatre règles :

1. **Mesurer d'abord le terrain réel.** Qu'est-il arrivé cette nuit ? Qu'a vu le plugin en
   production ?
2. **Vérifier le chemin de production, pas celui des tests.** Les tests d'hier appelaient souvent le
   plugin directement. Hermès l'appelle-t-il vraiment de la même façon ?
3. **Démontrer chaque défaut sur le code déployé avant de le corriger**, puis prouver la correction
   sur le code corrigé. Pas de correction sur simple soupçon.
4. **Finir par le vrai modèle.** Un jeu de tests factices valide la mécanique, jamais le jugement.

## 5 — Inexactitudes documentaires corrigées

1. **`04-consolidation.md`, décision D2.** J'avais écrit que sans fournisseur explicite, une
   consolidation lancée par le cron « pourrait partir sur l'abonnement Claude ». **Faux** : la route
   automatique d'Hermès prend d'abord le fournisseur et le modèle principaux
   (`_resolve_auto_route`, priorité 1). La vraie raison est plus fine : si le fournisseur principal
   est **indisponible** (quota épuisé), la route automatique **basculerait en silence** sur une
   chaîne de secours. Avec le fournisseur explicite, la consolidation échoue franchement et le lot
   attend.
2. **`01-squelette.md`, `plugin.yaml`.** Présenté implicitement comme déclarant les crochets
   actifs ; en réalité informatif. Précisé, et la liste complétée.

## 9 — Leçons

1. **Un plugin validé sans trafic réel n'est pas validé.** La revue a commencé par constater que
   la production n'avait encore rien vu.
2. **Le vrai modèle trouve ce que les tests ne trouvent pas** — deuxième fois en deux jours
   (défaut G). La règle est maintenant écrite : aucune étape impliquant un modèle ne se termine
   sans passage réel.
3. **Une instruction n'est pas un souvenir.** Tout message de contrôle (consigne, commande) doit
   rester hors de la matière première de la mémoire — il y fausse le contexte des souvenirs voisins.
